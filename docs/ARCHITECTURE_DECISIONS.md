# Architecture Decision Records (ADRs) — JobScout Bot

Документ фиксирует фундаментальные архитектурные решения, обоснование выбора технологий и компромиссы (trade-offs).

---

## ADR 001: Выбор библиотеки очередей задач (arq vs Celery vs Taskiq)

### Контекст
Бот выполняет ресурсоёмкие и асинхронные задачи:
1. Периодический краулинг внешних площадок по расписанию.
2. Рассылка уведомлений пользователям с соблюдением Telegram Rate Limits (30 сообщ/сек).
3. Ингестия вакансий и вычисление SimHash дубликатов.

### Рассмотренные альтернативы
1. **Celery**:
   - *Плюсы*: зрелость, огромная экосистема.
   - *Минусы*: исторически синхронный/multiprocessing дизайн, тяжеловесный брокер, проблемы с `asyncio`-корутинами в Python 3.12/3.13, избыточная сложность для задач среднего объёма.
2. **Taskiq**:
   - *Плюсы*: современный, полностью асинхронный.
   - *Минусы*: менее зрелая кодовая база, меньшее комьюнити.
3. **arq**:
   - *Плюсы*: нативный асинхронный движок поверх `redis-py` (asyncio), минимальный overhead, встроенный exponential backoff, ограничение конкурентности (`max_jobs`), идеальная совместимость с `asyncpg` и `aiogram 3`.

### Решение
Выбран **arq** в качестве основного движка очередей фоновых воркеров (`worker-crawler` и `worker-notifier`), с возможностью локального dev-запуска APScheduler в процессе бота при отсутствии Redis.

## ADR 002: Стек хранения данных: PostgreSQL + PgBouncer против SQLite

### Контекст
В dev-режиме критична простота быстрого локального запуска без внешних демонов (Zero-Dependency SQLite).
В продакшн-окружении (`ENV=prod`) множественные воркеры (`bot`, `scheduler`, `worker-crawler`, `worker-notifier`) одновременно пишут и читают данные, вызывая проблемы блокировок и исчерпания соединений.

### Решение
1. **Двухуровневый режим БД**:
   - `ENV=dev`: SQLite с включённым WAL-режимом (`PRAGMA journal_mode=WAL`) и увеличенным таймаутом ожидания блокировки (`busy_timeout=5000`).
   - `ENV=prod`: PostgreSQL 16 через асинхронный драйвер `asyncpg`.
2. **PgBouncer**:
   - Вынесен в `docker-compose.yml` в режиме `pool_mode = transaction`.
   - Пулы соединений SQLAlchemy настроены (`pool_size=10, max_overflow=5`), чтобы суммарное число соединений со всех сервисов не превышало лимиты PostgreSQL.
3. **Alembic**:
   - Отказ от `Base.metadata.create_all()` в продакшене. Все изменения схемы управляются версионированными миграциями.

## ADR 003: Разделение Ingestion (Crawler) и Search (On-demand)

### Контекст
В начальной версии бота поиск выполнялся синхронно по всем 9 площадкам в момент пользовательского запроса `/search`. Это приводило к лагам до 8-15 секунд, рискам 429/капчи при росте числа пользователей и дублированию запросов.

### Решение
Архитектура разделена на две независимые подсистемы:
1. **Ingestion Pipeline**:
   - Фоновые воркеры обходят площадки по стабильным «корзинам» (профессия × город × remote).
   - При ингестии сразу вычисляются: нормализация города, SimHash описания, canonical_id, детектирование грейда и требуемого опыта.
   - Схлопывание дубликатов между источниками на уровне БД.
2. **Search Pipeline**:
   - Сначала ищет по готовой дедуплицированной локальной базе `vacancies`.
   - При нехватке свежих карточек (`< 15`) выполняет догрузку с кэшированием результатов в Redis (`SEARCH_CACHE_TTL_MINUTES=20`).
   - Защита внешних площадок через `TokenBucket` и `CircuitBreaker`.

## ADR 004: Гибридный парсинг резюме (Regex + LLM)

### Контекст
Парсинг резюме только через LLM создаёт дорогостоящую зависимость от платных API, нестабильную латентность и риски утечки персональных данных. Парсинг только через регулярные выражения не всегда справляется с нестандартными формулировками.

### Решение
Реализован гибридный конвейер:
1. **Первый эшелон (Rule-based Regex & Heuristics)**:
   - 100% локальный, бесплатный, миллисекундный.
   - Извлекает стек технологий по справочнику canonical skills, вычисляет стаж через интервальное объединение (Interval Union).
   - Оценивает метрику уверенности `confidence_score` (0.0..1.0).
2. **Второй эшелон (LLM)**:
   - Запускается **только** с явного согласия пользователя (`llm_consent=True`) при низкой уверенности эвристик.
   - Абстракция `LLMProvider` поддерживает `OpenAI`, `YandexGPT`, `GigaChat`.
   - Входные данные очищаются от Prompt Injection (`sanitize_llm_input`) и персональных данных.

## ADR 005: Монетизация через Telegram Stars и система Entitlements

### Контекст
Для запуска платных функций в Telegram-боте (AI-письма, Gap-анализ, канбан-трекер) классический эквайринг (ЮKassa, Stripe) требует открытия юрлица, регистрации онлайн-касс и прохождения модерации.

### Решение
1. **Telegram Stars (XTR)**:
   - Встроенный платёжный инструмент Telegram, работающий для физических лиц.
   - Валюта `XTR`, тарифы `PRO` (150 Stars) и `TEAM` (400 Stars).
   - Обработка через `PreCheckoutQuery` и `SuccessfulPayment`.
2. **Архитектура Entitlements**:
   - Права доступа развязаны с конкретным платёжным шлюзом.
   - Модель `Entitlement` даёт гранулярный доступ к конкретным продуктовым фичам (`ai_cover_letter`, `ai_gap_analysis`, `kanban_tracker`).
   - Сторонние провайдеры (`YooKassaProvider`, `CryptoBotProvider`) спрятаны за единым интерфейсом `BasePaymentProvider` и выключены по умолчанию под feature-флагами.
